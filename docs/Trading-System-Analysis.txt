WHAT THIS SYSTEM IS
-------------------
The architectural refactor is implemented: pure strategy, historical research, and live
execution are separate crates. Candidate #2 is composed in-process by btc_price_ma_app; the
generic runner and trading_engine do not depend on strategy_core or research crates.

Three git repositories have distinct roles:
  trading_system     — models, research, live runner, risk, journal, ledger, proto
  k-paper            — local Paper exchange / deterministic fault lab
  trading-system-ui  — browser operator UI (not exchange authority)

k-paper is the local futures/fault laboratory. Bybit Demo is a bounded operational lab,
not mainnet. Flatten RPC success is not treated as flat.

The system is not production complete and is not mainnet ready. Candidate #2 is an
operational baseline, not validated alpha.


OPERATOR FLATTEN
----------------
One journaled reduce-only path in trading_engine (not trading_core). FlattenAndPause,
restart flatten, TRADING_FLATTEN, and the former gRPC TSM fallback persist client ID and
operator_flatten intent before send; recover by client ID. Acknowledged becomes Terminal
after a verified fill or flat venue. FlattenAndPause reports CancelWorking unverified
(including failed /open_orders), keeps the latch held, and does not send reduce-only.


DECOUPLING (implemented)
------------------------
strategy_core: ModelState + CompletedCandle -> decision. No exchange, runtime, or
research accounting.

Close-window API: on_candle(state, lookback, window) requires window.len()==lookback.
Primary N=28 uses exactly 28 completed daily closes including the current complete.
log_spread is ln(current) minus the mean of ln(closes) over that window. A short
window is an error, not NotReady. Forming-bar drop, wall-clock as_of, and
max_entry_age_secs belong to the adapter, not strategy_core. First ready live step
from a series that initializes N then steps needs N+1 completed bars (29 for N=28).

research_engine / research_cli: historical evaluation. Do not link the live runner.

btc_price_ma_app: Candidate #2 adapter injected into the generic runner in one process.
Use this binary for Shadow/Paper/Demo Candidate #2. The default runner binary does not
instantiate Candidate #2.

runner + trading_engine: live orchestration, risk, orders, journal, ledger, reconciliation.
No dependency on strategy_core, research_engine, research_cli, or btc_price_ma_app.

Operator path: trading-system-ui -> Envoy gRPC-Web -> runner gateway. Mutating RPCs on
non-Paper venues require TRADING_OPERATOR_TOKEN at the proxy/runner. The UI login is not
that authorization. The legacy TUI is a separate gRPC client; the browser UI is the
operator console.

Python strategy_dsl / architecture/10-strategy-engine.md is a separate proposed IR path,
not the Candidate #2 model.
